01Context

Operational and financial data was spread across 12+ data sources: REST APIs, files in object storage, and exports arriving by email, each in its own shape and on its own schedule.

Teams pulled this data by hand, aggregated it, and built client reports, work that took hours to days. A recurring month-end process ran off the same manual exports. There was no shared warehouse and no application on top of it. I built both.

02Data Pipeline Platform
System 1 / ETL & ELT

A production platform that ingests from 12+ data sources into a cloud data warehouse holding 400M+ rows across 6 years, and keeps it current on unattended nightly runs.

A modular ingestion framework

A connector → processor → enrichment → loader pipeline with fetch-first idempotency, retry with backoff, and memory-safe chunked bulk loading, so nightly jobs run without a human watching them.

Unattended nightly ingestion across 12+ data sources

Fault-tolerant historical backfills

Ran large backfills (34M+ rows) at per-day granularity with fault tolerance, so a failure resumes instead of restarting and source rate limits are respected.

6 years of history loaded without tripping source rate limits

Nightly ERP integration

An ERP system over ODBC → warehouse job on a systemd timer loading raw tables, with certified SQL views validated against source exports so downstream numbers match the system of record.

ERP financials in the warehouse, reconciled to source

Anomaly detection and observability

A data-anomaly detection and correction framework (fix-at-source vs. override) with an append-only audit ledger, plus cloud logging and threshold alarms. Diagnosed warehouse saturation and specified staged bulk-load and sort-key optimizations.

Corrections are traceable; saturation was measured, not guessed

03Full-Stack Analytics Platform
System 2 / FastAPI + React on AWS

A FastAPI and React/TypeScript application live on a public HTTPS domain for internal teams. I provisioned and secured the full cloud stack on AWS: compute, a managed OLTP database, a load balancer, TLS, object storage, and container-based deployment. 04Hot / cold two-tier architecture

The app can't query a 400M+ row warehouse live, but it does need current data. So I split serving from storage. The cold tier is the full cloud data warehouse. The hot tier is the most recent year (about 58M rows) mirrored into a managed OLTP database, which serves live application queries.

The naive way to keep the hot tier fresh, a direct row-by-row warehouse-to-OLTP transfer, benchmarked at roughly 1 hour per data source per month, which extrapolates to about 24 hours for a single year across 7+ sources. That was a non-starter for a nightly job.

Instead of row-by-row inserts, I built warehouse unload → compressed columnar files in object storage → parallel bulk load into the OLTP database, replacing millions of individual inserts with a parallelized columnar export and load.

On top of that I added incremental sync by content fingerprinting. Data is partitioned by month in object storage, and each monthly partition carries a hash fingerprint. Each nightly run compares fingerprints and re-pulls only the months whose data actually changed, swapping partitions atomically and dropping stale data. Fingerprinting takes about 10 seconds per month and a full month re-pull about 50 to 60 seconds, so the worst case (all 12 months changed) is under 15 minutes and a typical night is under 5, against the ~24 hour baseline. That is roughly a 99% reduction.

Monthly granularity was a deliberate choice, matched to how the data actually mutates.

Data sources restate recent figures (metrics get revised days later from timezone lag or source-side outages), which I handle upstream with a rolling 30-day re-pull into the warehouse. After about 30 days the data is effectively immutable, so only the most recent month or two ever have changed fingerprints.

Fingerprints also catch my own corrections, like fixing mislabeled records surfaced by anomaly detection, which can touch any month. That makes the serving layer self-healing regardless of where or why the data changed.

05Impact

The reporting teams retrieve their data on demand in seconds instead of assembling it by hand over hours to days. The recurring month-end process dropped from days to hours. The serving layer stays current on a nightly job that runs in minutes, and the whole stack runs in production for internal teams.
